# 中断共享变量的原子访问

## 结论

`volatile` 不能保证原子性。它只保证编译器按程序要求真实访问变量，不会把中断更新的值长期缓存到寄存器；但它不能保证多字节读写不会被打断，也不能把“读取、判断、清零”变成一个不可拆分的原子动作。

本工程基于 Keil C51/MCS-51 8 位 MCU。共享变量通常出现在中断更新和主循环消费之间，例如 TMR1 中断递增计数器，主循环在固定周期触发任务。由于 16 位变量需要多次字节访问，读取本身就可能撕裂；即使读到完整值，若中断在判断和清零之间又写入新值，旧事件也可能被覆盖掉。

所以，本工程里的结论非常明确：

- `volatile` 只是“共享标志”，不是“线程安全/原子安全”；
- 共享状态的“读-判-写”或“读-改-写”复合操作，必须收敛到临界区；
- 当前工程已经提供了统一的 `ENTER_CRITICAL_SECTION()` / `EXIT_CRITICAL_SECTION()`，后续共享变量应优先用它们。

## 当前工程中的真实竞态场景

在本工程里，TMR1 周期中断会递增计时器，主循环再在合适时机消费它。实际代码在 [Hardware/tmr1.c](Hardware/tmr1.c) 中调用：

```c
#if FUEL_CAPACITY_SCAN_ENABLE
    fuel_capacity_scan_time_add();
#endif
```

对应实现位于 [User/fuel_capacity.c](User/fuel_capacity.c) 中：

```c
static volatile u8 fuel_capacity_scan_time_cnt = 0;

void fuel_capacity_scan_time_add(void)
{
    if (fuel_capacity_scan_time_cnt < ((u16)-1)) {
        fuel_capacity_scan_time_cnt++;
    }
}
```

而主循环的消费逻辑又是：

```c
if (fuel_capacity_scan_time_cnt >= FUEL_SCAN_PERIOD) {
    fuel_capacity_scan_time_cnt = 0;
} else {
    return;
}
```

这里就存在典型的竞争窗口：

- 主循环检测到计数达到阈值；
- 还没执行清零前，TMR1 中断又执行一次 `fuel_capacity_scan_time_add()`；
- 主循环随后把计数清零，导致新一轮周期被“吞掉”；
- 由于 8 位 MCU 的 16 位变量访问并非单条指令，读取/比较/赋值过程本身也可能被打断。

这和常见的 `if (cnt >= PERIOD) { cnt = 0; }` 竞态完全一致，`volatile` 不能修复它。

## 本工程里已经形成的安全模板

本工程在 [User/user_config.h](User/user_config.h) 中定义了统一临界区宏：

```c
#define ENTER_CRITICAL_SECTION()                                               \
    do {                                                                       \
        irq_was_enabled = IE_EA;                                               \
        IE_EA = 0;                                                             \
    } while (0)
#define EXIT_CRITICAL_SECTION()                                                \
    do {                                                                       \
        IE_EA = irq_was_enabled;                                               \
    } while (0)
```

这个设计的关键点是：

- 先保存进入前的全局中断状态；
- 关闭总中断；
- 在同一临界区内完成共享变量的检查和更新；
- 退出前恢复原来的中断状态，而不是无条件写 `IE_EA = 1`。

这正是当前工程对共享变量的推荐用法。

## 推荐写法：在同一临界区内完成检查与清零

对于类似油量扫描这样的周期计时器，推荐写法是：

```c
void fuel_capacity_scan(void)
{
    u16 fuel_adc_val;
    u16 fuel_voltage;
    u8 fuel_percent;
    u8 scan_due = 0;

    ENTER_CRITICAL_SECTION();
    if (fuel_capacity_scan_time_cnt >= FUEL_SCAN_PERIOD) {
        fuel_capacity_scan_time_cnt = 0;
        scan_due = 1;
    }
    EXIT_CRITICAL_SECTION();

    if (scan_due == 0) {
        return;
    }

    /* 后续 ADC 采样、滤波、换算和界面更新逻辑 */
}
```

这个写法的重点是：

- 读取、比较、清零都在同一个临界区内完成；
- 中断在临界区期间不会插入新的递增操作；
- 退出临界区后再进行较重的处理，避免占用中断关闭时间太久；
- 要保留原先的中断状态，而不是强行打开或强行关闭。

## 本工程中已采用的安全实践

[User/engine_speed_scan.c](User/engine_speed_scan.c) 里已经是更完整的安全典范：

```c
ENTER_CRITICAL_SECTION();
if (pending_engine_speed_scan_ms != 0 ||
    flag_is_engine_speed_scan_over_time) {
    scan_pulse_snapshot = pending_engine_speed_scan_cnt;
    scan_time_snapshot = pending_engine_speed_scan_ms;
    is_scan_over_time = flag_is_engine_speed_scan_over_time;

    pending_engine_speed_scan_cnt = 0;
    pending_engine_speed_scan_ms = 0;
    flag_is_engine_speed_scan_over_time = 0;
    scan_due = 1;
}
EXIT_CRITICAL_SECTION();
```

这里不是单独“看一眼变量”，而是把：

- 读取快照；
- 清空待处理状态；
- 标记任务已触发；

放在同一临界区里处理，以避免事件丢失或统计被覆盖。

## 关键注意事项

- `volatile` 不能替代临界区。
- 只有单字节读写才接近“天然原子”，但“检查后清零”仍然是复合操作。
- 多字节共享变量必须做快照、判定和更新的一体化保护。
- 临界区必须尽可能短，只包住共享状态处理，不要把 ADC、滤波、打印或 UI 更新放在关闭中断期间。
- 若业务需求是“保留余数而不是直接清零”，可以在临界区内读取并做减法；但必须明确饱和、回绕和追赶策略。

## 对本工程的建议

当前工程的整体方向是对的：

- 用 `volatile` 表达“共享关系”；
- 用 `ENTER_CRITICAL_SECTION()` / `EXIT_CRITICAL_SECTION()` 作为统一的保护接口；
- 对“看值 + 清零/消费”这类复合操作，必须成对放入临界区；
- 对任何新加的共享计数器、事件标志或多个字节结构体，都应先确认是否涉及读-改-写。

简而言之，`volatile` 负责“让编译器不要偷懒”，但真正保证正确性的，是临界区和一致性的复合操作保护。对本工程而言，这条原则必须坚持到所有中断共享变量上。
